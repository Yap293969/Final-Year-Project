## PhishTank Acquisition Module (2026-08-18)

**`src/data/phishtank.py`** — reusable, callable from any notebook or script:

```python
from src.data.phishtank import fetch_phishtank_dataset
df = fetch_phishtank_dataset()                    # reuses a recent snapshot
df = fetch_phishtank_dataset(force_refresh=True)  # forces a new download
path = fetch_phishtank_dataset(load=False)        # raw file path only
```

| Aspect | Implementation |
| --- | --- |
| Source | `http://data.phishtank.com/data/online-valid.csv` |
| Authentication | keyless by default; `PHISHTANK_APP_KEY` inserted into the path only if set; key redacted before logging or writing |
| User-Agent | `phishtank/fyp2-anti-phishing-research`, overridable via `PHISHTANK_USER_AGENT` |
| Raw snapshot | `data/raw/phishtank/online-valid_<UTCSTAMP>.csv`, exact bytes, never overwritten |
| Metadata | `data/metadata/phishtank/<name>.json` — source URL, retrieval time, filename, size, HTTP status, ETag, SHA-256, whether a key was used, runtime |
| Failed attempts | recorded as `FAILED_<stamp>.json`, so unsuccessful acquisition stays in the research record |
| Caching | a snapshot younger than `max_age_hours` (default 6) is reused; `force_refresh=True` overrides |
| Payload validation | downloads to a temp file first; rejects HTML/XML bodies and headers missing the documented fields, so a Cloudflare page served with HTTP 200 can never be stored as data |
| Return value | `pandas.DataFrame` with provenance in `df.attrs`, or `Path` when `load=False` |
| Scope | download → save → metadata → load only; no cleaning, feature engineering, splitting or modelling |

**Module test result (2026-08-18): 34 of 34 assertions passed** against a local HTTP
server serving a synthetic feed with the real PhishTank schema — covering successful
acquisition, byte-exact preservation, SHA-256, metadata completeness, pandas load, all
eight expected columns, cache reuse, `force_refresh` without overwrite, rejection of a
Cloudflare 200/HTML payload, and an actionable 403. Synthetic data was written to a
temporary root and never entered `data/raw/`.

**Live feed result: FAILED — HTTP 429 (rate limited)**, at 03:16 and 03:19 UTC on
2026-08-18. No real snapshot exists, so the module's behaviour on genuine PhishTank
data is verified only against the synthetic fixture.

## Primary Email Dataset Decision (2026-09-10)

**Chosen: candidate A's six corpora.** 82,486 rows, intact message bodies, and a subject
field. Recorded here as required before preprocessing could begin.

The decision rests on a full-pass measurement of text representation taken on 2026-09-10,
which corrected an assumption in the previous entry. Candidate A does **not** hold six raw
corpora — it holds four:

| Corpus | Rows | Rows with an uppercase letter | Rows with spaced punctuation | Representation |
| --- | ---: | ---: | ---: | --- |
| A/CEAS_08 | 39,154 | 98.55% | 3.14% | raw |
| A/Nazario | 1,565 | 99.04% | 12.46% | raw |
| A/Nigerian_Fraud | 3,332 | 99.91% | 24.73% | raw |
| A/SpamAssasin | 5,809 | 99.78% | 7.13% | raw |
| A/Enron | 29,767 | **0.00%** | 92.79% | pre-normalised |
| A/Ling | 2,859 | **0.00%** | 99.30% | pre-normalised |
| A/phishing_email | 82,486 | 0.00% | 0.00% | normalised **and punctuation stripped** |
| B/Phishing_Email | 18,650 | 29.59% | 66.43% | mostly normalised |

Why the six corpora win anyway:

* **The aggregated file is excluded outright.** 0.00% spaced punctuation means its
  punctuation is not spaced out but *deleted*, and that is unrecoverable. BERT needs raw
  text (Specification §9).
* **Candidate B was rejected**: 4.4× less data, no subject field, and 66.43% of its rows
  already punctuation-spaced.
* **The mixed representation inside candidate A is a measured, accepted limitation.**
  `bert-base-uncased` lower-cases its input, so the tokeniser removes the casing half of
  the difference before the model sees it. Casing was also measured to be a *weak* label
  predictor — 56.60% phishing among cased rows against 45.18% among lower-cased rows — not
  the near-perfect source detector the URL scheme was.

### Decisions recorded for this stage

| Decision | Choice | Why |
| --- | --- | --- |
| Feature selection | **none** | XGBoost receives all 35; the separation ranking drops nothing |
| Constant features | reported, **not removed** | measured: none of the 35 is constant |

### Interpretation

1. **The proposed BERT + XGBoost system works.** F1 0.9846 on email and 0.9641 on URLs,
   against floors of 0.6793 and 0.0000.

2. **It did not beat the TF-IDF baselines.** `email_tfidf_logreg` leads by 0.0022,
   `url_tfidf_logreg` by 0.0037. Small margins, but in the baselines' favour. Recorded as
   the result; no claim is made that the proposed system is better (CLAUDE.md rules 3
   and 4).

3. **The hybrid beats each of its own parts - the Objective 2 result.** On URLs, BERT +
   lexical (0.9641) beats lexical-only XGBoost (0.9366) by 0.0275 and BERT-only (0.9587)
   by 0.0054. Combining contextual with structural features helps; it does not overtake a
   character n-gram baseline on this data.

4. **Test agrees with validation on all eleven models.** Largest gap 0.0091
   (`url_lexical_logreg`), most under 0.003. The section 6 splits are clean and nothing
   was quietly fitted to validation.

5. **The BERT models overfit.** `email_bert` reaches train F1 1.0000 against validation
   0.9847; both URL BERT models sit near 0.997 on train. They still generalise, but there
   is headroom. Not pursued: tuning after the test split was opened would invalidate the
   measurement.

6. **Why a classical baseline can win here.** Two measured reasons, not speculation. The
   TF-IDF baselines read the **whole** email while the BERT branch truncates at 256 tokens
   (about 55% of emails fit whole), and on short token-like strings such as URLs character
   n-grams are a strong representation while a **frozen** BERT never adapts to the task.
   Fine-tuning BERT is the obvious next experiment and lies outside the approved
   architecture.

7. **Read every URL number against known problem 14** (the benign and phishing URLs come
   from different sources).

### What this supports, and what it does not

* Supported: the proposed system detects phishing emails and URLs at high accuracy, and
  the BERT + lexical combination improves on either component alone.
* Not supported: any claim that BERT + XGBoost outperforms classical baselines on this
  dataset. The measurement says the opposite, by a small margin.

### Which model it serves, and why that is a decision

`MODEL_SELECTION_POLICY` in 12.3 is set to `"proposed"`. The prototype therefore serves
the best **measured** model that uses the approved BERT + XGBoost architecture, not the
best measured model overall.

This matters because the two are no longer the same. Under `"best_measured"` the
prototype would serve `email_tfidf_logreg` and `url_tfidf_logreg` - and this project's
prototype would contain no BERT and no XGBoost at all. The setting is documented in the
cell, both options are implemented, and the interface **states on screen** that a baseline
scored slightly higher, with its F1. The gap is disclosed, not hidden behind the choice.

Neither model is named by hand: both are read from the section 11 report and chosen by
measured test F1 within the policy.

### Train / serve skew, and how it is prevented

The failure this section is built against: a model that scores well in section 11 but
answers nonsense behind a form, because typed input is prepared differently from the rows
it learned on. Section 6 stripped the scheme and trailing slash from every URL and joined
each email subject to its body. A model trained on `paypal-login.com/verify` has never
seen `https://paypal-login.com/verify/`.

The prototype re-implements none of that. It calls the same `normalise_url`,
`join_subject_and_body` and `clean_text` used to build the training data. Section 12.2
proves it against **200 real processed rows**: a URL pasted with an `https://` scheme
normalises to the stored training form in all 200 cases.

### Honesty and safety of the interface

* Every tab names the model that answered and quotes its measured test F1 and accuracy.
* Every tab carries a disclaimer that this is a research prototype, not a security
  product, and can be wrong in both directions.
* A URL answer lists plain-language warning signs drawn from the section 7 features, so a
  young user learns what to look at rather than being handed a verdict. The rules are
  written as data and 12.2 asserts every feature name exists in `FEATURE_NAMES`, because a
  mistyped name would read as zero and the message would silently never appear.
* User input is never echoed into the result card, so nothing typed can alter the markup.
  The email *explanation* card (12.4) must show the user's words, so every word is passed
  through `html.escape()`; 12.5 and 12.7 test that pasted `<script>` and `<div>` text is
  shown as text and cannot unbalance the card.

### Explanations (sections 12.4-12.5, added 2026-10-10)

| Item | Links (`url_bert_lexical`) | Emails (`email_bert`) |
| --- | --- | --- |
| Method | TreeSHAP built into XGBoost, `pred_contribs=True` | `shap` Partition explainer over the whole text -> BERT -> XGBoost path |
| Exact? | yes | approximate; detail depends on the budget |
| What is shown | the 768 BERT contributions **summed** into one item, plus each of the 35 lexical features by name | each word coloured by its push, plus the top words each way |
| Cost | milliseconds, shown with the verdict | `EMAIL_EXPLAIN_MAX_EVALS` BERT re-scorings (100 on CPU, 300 on GPU), on a separate "Explain why" button |
| Text limit | - | cut to what BERT reads (256 tokens), at a word boundary |

Values are in **log-odds**, never shown as percentages. Positive pushes towards phishing.
The 768 BERT values are summed because one BERT dimension has no meaning to a reader;
SHAP values are additive, so the sum is exact.

The fixed warning rules from 12.1 are kept but now headed **"General warning signs
(fixed rules, not the model's reasons)"**, because they can contradict SHAP: section 7
measured phishing URLs here as *shorter* than legitimate ones (49.67 vs 56.82), so the
`url_length` rule can point the opposite way to what the model learned.

What 12.5 proves, on 50 real **validation** rows (never test): pushes add up to the
model's raw score; that score gives the probability shown; its sign matches the
verdict; the BERT block is 768 columns wide and the named columns hold exactly the
section 7 feature values, so no feature name can be attached to the wrong number.

**Rule kept:** nothing about the models may be changed in response to what SHAP shows.
The test split has been opened, so retraining or dropping features now would invalidate
section 11. Explanations are reported as what the model does, not as a reason to tune.

* Do not change the BERT + XGBoost methodology without justification.
* Do not report results before actual experiments are executed.
* Do not use test data during model development.

* Scope limited to an undergraduate FYP research prototype.
